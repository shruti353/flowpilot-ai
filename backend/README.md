# FlowPilot AI - Backend

FlowPilot AI turns a free-text request into a structured execution plan,
holds it for **explicit human approval**, and - only after that approval -
can perform one real, narrowly-scoped external action through n8n.

- **Week 1** — text in, validated structured plan out. No execution.
- **Week 2** — the plan is *persisted* and sits `awaiting_approval` until
  a human approves, rejects, or cancels it. Still no execution.
- **Week 3** (this update) — an `approved` plan can be explicitly
  executed. Real execution exists ONLY for `calendar.create_event`,
  performed via an n8n webhook that creates a Google Calendar event.
  Every other tool/operation is reported as unsupported, never silently
  skipped or faked as successful.

No Gmail execution, no task-app integration, no database, no auth,
no queues, no autonomous execution anywhere in this codebase.

## 1. What's implemented

**Week 1 - planning**
- `POST /api/v1/agent/plan`: an explicit, linear LangGraph workflow
  (`UNDERSTAND_REQUEST -> GENERATE_PLAN -> VALIDATE_PLAN`, no loops, no
  branching, no multi-agent orchestration) turns text into a plan using a
  local LLM (Ollama). The raw LLM output is never trusted - it's always
  parsed and re-validated with Pydantic.
- A fixed catalog of three logical tools (`calendar`, `tasks`, `email`)
  with a fixed set of operations each (see the support matrix in section
  9). Anything outside that catalog is rejected with a structured error.
- Requests missing required details (e.g. "schedule a meeting tomorrow"
  with no title) still produce a plan, with the missing fields listed
  instead of an invented value.

**Week 2 - human-in-the-loop approval**
- Every plan generated by `POST /api/v1/agent/plan` is persisted (in
  memory) and comes back with a lifecycle `status`.
- `GET /api/v1/plans/{plan_id}` retrieves a stored plan and its status.
- `POST /api/v1/plans/{plan_id}/approve` / `.../reject` / `.../cancel`
  move a plan through its lifecycle. Pure state transitions - no tool is
  ever called.

**Week 3 - approval-gated real execution**
- `POST /api/v1/plans/{plan_id}/execute` runs an `approved` plan's
  actions **exactly once**. It:
  - Normalizes any natural-language datetime (e.g. "tomorrow at 3 PM")
    into a concrete, timezone-aware ISO 8601 datetime using deterministic
    application logic - never the LLM.
  - Dispatches each action to a real adapter if one is registered
    (today, only `calendar.create_event` -> n8n -> Google Calendar), or
    reports `EXECUTION_NOT_SUPPORTED` otherwise.
  - Updates plan/action state to `executed`, `partially_executed`, or
    `execution_failed`, and is safe against duplicate execution.
- The LLM and LangGraph never see Google credentials, never call n8n,
  and never decide whether a plan may execute.

## 2. Architecture

```
USER
 |
 v
GENERATE PLAN        (LangGraph + Ollama - unchanged since Week 1)
 |
 v
VALIDATE PLAN        (Pydantic - unchanged since Week 1)
 |
 v
STORE PLAN           (app/repositories/plan_repository.py - in memory)
 |
 v
AWAITING APPROVAL
 |
 +-------------------+
 |                   |
APPROVE            REJECT / CANCEL
 |                   |
APPROVED           REJECTED / CANCELLED
 |
 v  (POST .../execute)
EXECUTING
 |
 v
EXECUTION SERVICE    (app/services/execution_service.py - deterministic,
 |                     no LLM, prevents duplicate execution)
 v
EXECUTION ADAPTER     (app/execution/adapters/n8n_calendar.py)
 |
 v
n8n WEBHOOK
 |
 v
GOOGLE CALENDAR
 |
 v
EXECUTED / PARTIALLY_EXECUTED / EXECUTION_FAILED
```

Full request path for planning:

```
Text Input -> FastAPI -> LangGraph -> Ollama -> Structured Plan
           -> Pydantic Validation -> Plan Repository -> JSON Response
```

Planning (the AI's job), approval (a human's job), and execution (a
deterministic service's job) are three separate layers. LangGraph only
ever produces a plan. Approving/rejecting/cancelling is plain state logic
in `approval_service.py`. Executing is plain state + I/O logic in
`execution_service.py` + `app/execution/*`. **The LLM is never in the
execution path** - it cannot call n8n, cannot see Google credentials, and
is never asked to decide whether something may run.

### Execution architecture

```
app/execution/
├── result.py           ActionExecutionResult, PlanExecutionResult
├── dispatcher.py        (tool, operation) -> adapter registry
├── executor.py          runs one action: dispatch or EXECUTION_NOT_SUPPORTED
├── n8n_client.py         HTTP client for n8n webhooks (swappable for tests)
└── adapters/
    ├── base.py          ExecutionAdapter interface, ExecutionContext
    └── n8n_calendar.py  calendar.create_event -> n8n -> Google Calendar

app/services/execution_service.py
    - claims a plan for execution (approved -> executing), atomically
    - runs every action through app/execution/executor.py
    - summarizes the outcome and writes the final plan/action state
```

`ExecutionContext` passed to every adapter carries only
`request_id`, `plan_id` - never conversation history, prompts, or LLM
reasoning. The n8n payload (see section 8) carries only the fields
needed to create one calendar event.

### Plan lifecycle / state machine

`StoredPlanStatus` (`app/models/stored_plan.py`):

```
                 valid, all info present
                          |
                          v
                 awaiting_approval ------> approved ------> executing
                          |                                    |
                          +--------------> rejected             +--> executed
                          |                                     |
                          +--------------> cancelled             +--> partially_executed
                                                                  |
  valid, missing info --> needs_clarification (never approvable) +--> execution_failed

  failed validation   --> error                     (never approvable/executable)
```

- `executing` is transient: a single synchronous `/execute` call moves a
  plan through it on the way to one of the three terminal outcomes. No
  plan should ever be observed sitting in `executing` between requests.
- `executed`: every action succeeded. `partially_executed`: at least one
  succeeded and at least one failed/was unsupported. `execution_failed`:
  no action succeeded (all failed, all unsupported, or a mix).
- **Only a plan in `approved` may be executed.** `awaiting_approval`,
  `needs_clarification`, `rejected`, `cancelled`, `error`, and every
  execution outcome (`executing`, `executed`, `partially_executed`,
  `execution_failed`) all reject a second `/execute` call with `409`.
  This is what prevents duplicate execution - see below.

Action-level execution statuses (`app/execution/result.py`):
`pending`, `executing`, `succeeded`, `failed`, `skipped`, `unsupported`.

### Duplicate-execution safety

`PlanRepository.compare_and_update` (`app/repositories/plan_repository.py`)
atomically checks a plan's current status and writes its new status under
a single lock acquisition. `ExecutionService` uses it to claim
`approved -> executing` before calling any adapter. Two `/execute`
requests racing for the same `plan_id` can't both pass that check - the
second always observes a non-`approved` status and is rejected with `409`
before any adapter or n8n call happens. This was verified under test with
a fake n8n client that records call counts (see section 11).

## 4. Prerequisites

- Python 3.11+
- Node.js 18+ (for the frontend)
- [Ollama](https://ollama.com) installed and running locally
- [n8n](https://n8n.io) (only needed to actually execute
  `calendar.create_event` - see section 7)

## 5. Install Ollama and pull a model

```bash
ollama pull llama3.2:3b
```

| `N8N_BASE_URL` / `N8N_CALENDAR_WEBHOOK_PATH` | *(unset)* / `/webhook/flowpilot-calendar` | Alternative to the full URL above |

If neither `N8N_CALENDAR_WEBHOOK_URL` nor `N8N_BASE_URL` is set,
`calendar.create_event` fails execution with a structured
`N8N_NOT_CONFIGURED` error - it never silently does nothing.

## 7. n8n and Google Calendar setup

**n8n itself never runs inside this backend.** It's a separate service
FastAPI calls over HTTP.

1. Start n8n (no Docker required):
   ```bash
   npx n8n start
   ```
   n8n's editor is at http://localhost:5678 by default.
2. Import the workflow: in the n8n editor, **Workflows -> Import from
   File**, and select `workflows/flowpilot_google_calendar.json`. (Or use
   the CLI: `n8n import:workflow --input=workflows/flowpilot_google_calendar.json`.)
3. Configure Google Calendar credentials **inside n8n only**:
   - Open the imported workflow's "Create Google Calendar Event" node.
   - Under Credentials, create/select a **Google Calendar OAuth2 API**
     credential and complete the OAuth consent flow. This is the only
     place Google OAuth client secrets and refresh tokens are ever
     configured - never in this backend's `.env`, never in a prompt.
   - Pick the target calendar (the node defaults to `primary`).
4. Activate the workflow (toggle in the top-right of the editor). This
   registers the production webhook at
   `http://localhost:5678/webhook/flowpilot-calendar`.
5. Point the backend at it: set `N8N_CALENDAR_WEBHOOK_URL` in `.env` to
   that URL (already the default in `.env.example`).

The workflow itself (see the JSON for the exact node graph):

```
FastAPI Webhook Request
        |
        v
Validate Payload (Code node - checks tool/operation/required fields)
        |
   (valid) --------------------> (invalid)
        |                              |
        v                              v
Create Google Calendar Event    Respond Invalid Payload
        |
   (success) ------------------> (failure)
        |                              |
        v                              v
  Respond Success              Respond Calendar Failure
```

Both failure-response nodes return HTTP 200 with
`{"success": false, "error_code": "...", "message": "..."}` (not a 4xx/5xx)
so FastAPI can surface the specific reason rather than a generic HTTP
error. The success node returns:
```json
{"success": true, "external_event_id": "...", "html_link": "...", "message": "Calendar event created successfully"}
```

**If you'd rather build it by hand:** Webhook (POST, response mode
"Respond to Webhook") -> a Code/Function node that validates the payload
and rejects anything that isn't `calendar.create_event` with both `title`
and `start_datetime` present -> a Google Calendar node ("create" event,
start/end from the payload) -> two Respond-to-Webhook nodes shaped as
above for the success/failure branches.

**Verification note:** the exported JSON was validated by importing it
into a real local n8n instance via `n8n import:workflow` (confirms the
node/connection schema is valid) and end-to-end tested by pointing this
backend's `N8N_CALENDAR_WEBHOOK_URL` at a minimal mock HTTP server that
returns exactly the success/failure shapes above - this proved the full
FastAPI -> HTTP -> response-parsing contract for real. Live-firing the
*actual* imported workflow's webhook could not be completed in this
environment (the specific n8n build available here defers webhook
registration in a way that didn't reflect normal n8n activation
behavior); importing via the n8n **editor UI** as described above
follows n8n's standard activation path and is the supported route.

## 9. API endpoints

### `POST /api/v1/agent/plan` (Week 1/2, unchanged)
Generates and stores a plan. `status` is `awaiting_approval`,
`needs_clarification`, or `error`. See the Week 1/2 sections above for
the full response shape.

### `GET /api/v1/plans/{plan_id}` / `.../approve` / `.../reject` / `.../cancel`
Unchanged from Week 2. State transitions only, no execution.

### `POST /api/v1/plans/{plan_id}/execute` (new)

Executes an `approved` plan's actions exactly once.

- `404` (plan not found), `409 Conflict` with
  `{plan_id, message, current_status}` if the plan isn't `approved`
  (includes: not yet approved, rejected, cancelled, needs clarification,
  errored, or already executing/executed/partially_executed/failed).
- Otherwise, HTTP 200 with:

```json
{
  "plan_id": "...",
  "status": "partially_executed",
  "message": "Plan partially executed - at least one action succeeded, but at least one failed or is not yet supported.",
  "execution": {
    "status": "partial",
    "actions": [
      {
        "action_id": "action_1",
        "tool": "calendar",
        "operation": "create_event",
        "status": "succeeded",
        "result": {
          "external_event_id": "...",
          "html_link": "...",
          "start_datetime": "2026-08-23T15:00:00+05:30",
          "end_datetime": "2026-08-23T16:00:00+05:30"
        },
        "error": null
      },
      {
        "action_id": "action_2",
        "tool": "tasks",
        "operation": "create_task",
        "status": "unsupported",
        "result": null,
        "error": {"code": "EXECUTION_NOT_SUPPORTED", "message": "Execution is not implemented for tasks.create_task."}
      }
    ]
  },
  "plan": { "...": "full StoredPlan, same shape as GET /plans/{plan_id}" }
}
```

A plan with both a supported and an unsupported action is reported
exactly like this - `partially_executed`, never claimed as fully
successful. Other failure codes an action's `error.code` may carry:
`MISSING_PARAMETERS`, `DATETIME_NORMALIZATION_FAILED`,
`N8N_NOT_CONFIGURED`, `N8N_TIMEOUT`, `N8N_UNREACHABLE`,
`N8N_HTTP_ERROR`, `N8N_INVALID_RESPONSE`, or whatever `error_code` the
n8n workflow itself returned (e.g. `CALENDAR_API_ERROR`).

### Execution support matrix

| Tool | Operation | Can be **planned** | Can be **executed** |
|---|---|---|---|
| calendar | create_event | ✅ | ✅ (via n8n -> Google Calendar) |
| calendar | get_event | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |
| tasks | create_task | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |
| tasks | get_task | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |
| email | draft_email | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |
| email | send_email | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |
| email | search_email | ✅ | ❌ `EXECUTION_NOT_SUPPORTED` |

Adding real execution for another tool/operation means registering a new
adapter in `app/execution/dispatcher.py` - nothing in the API routes, the
LangGraph pipeline, or the frontend needs to change.

## 10. Datetime normalization

The LLM never computes "today" - `app/utils/datetime_parser.py` resolves
a raw string like `"tomorrow at 3 PM"` deterministically, using the real
current time (or an injected reference in tests) plus `FLOWPILOT_TIMEZONE`,
via the `dateparser` library with `RELATIVE_BASE` pinned explicitly. If
the result is ambiguous or unparseable, `normalize_datetime` raises
`DatetimeNormalizationError` - the adapter turns that into a `failed`
action result (`DATETIME_NORMALIZATION_FAILED`) and **does not call n8n**.
The original plan/action is left exactly as it was for debugging; nothing
is executed and no time is guessed.

## 11. Run tests

Tests mock the LLM provider (`ollama_service`) and the n8n HTTP client
(`execution.n8n_client`), and reset the in-memory plan repository between
tests. The whole suite runs without a live Ollama server, a live n8n
instance, or Google Calendar credentials.

```bash
cd backend
pytest
```

- `tests/test_api.py`, `tests/test_agent.py`, `tests/test_models.py` -
  Week 1 planning behavior.
- `tests/test_plans.py` - Week 2 approval lifecycle.
- `tests/test_datetime_parser.py` - deterministic datetime normalization.
- `tests/test_execution.py` - dispatcher/adapter unit tests, the full
  approve -> execute flow, every non-`approved` status rejecting
  execution, mixed-plan partial reporting, and duplicate-execution
  prevention (asserted via a fake n8n client's recorded call count).

## 12. Security notes

- Google OAuth client ID/secret and refresh tokens live **only** inside
  n8n's credential store. This backend never stores, reads, or forwards
  them, and they never appear in a prompt sent to Ollama.
- `.env`, OAuth client secrets, refresh tokens, and n8n credential
  exports must never be committed - only `.env.example` files with
  placeholder values. `backend/.gitignore` excludes `.env`.
- No authentication/authorization on this API yet - anyone who can reach
  it can approve/execute any `plan_id` they know. Fine for local
  development; not for exposing this API publicly as-is.

## 13. Current limitations

- **Storage is in-memory only.** Restarting the backend loses every
  stored plan, including execution results.
- Real execution exists only for `calendar.create_event`; every other
  tool/operation is planned but never executed (see the matrix above).
- Execution is synchronous - one HTTP request, no background queue, no
  retry-on-failure. A failed execution must be diagnosed and re-planned;
  there is no "retry this action" endpoint yet.
- No authentication/authorization.
- Datetime normalization depends on `dateparser`'s coverage of natural
  language; unusual phrasings may fail normalization (safely, as a
  structured `DATETIME_NORMALIZATION_FAILED`, never a guess).
- Plan quality depends on the chosen local Ollama model; smaller models
  may occasionally violate the JSON contract (surfaces as an `error`
  plan) or add actions beyond what was asked (observed with `llama3.2:3b`
  during testing - harmless, since anything unsupported is honestly
  reported rather than executed).
