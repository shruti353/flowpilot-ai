# FlowPilot AI - Backend

FlowPilot AI turns a free-text request into a structured execution plan,
then holds that plan for **explicit human approval**. Nothing is ever
executed automatically, in either phase implemented so far:

- **Week 1** — text in, validated structured plan out.
- **Week 2** (this update) — the plan is now *persisted* and sits
  `awaiting_approval` until a human approves, rejects, or cancels it.

No Google Calendar, no Gmail, no Todoist, no n8n, no database, no auth, no
real tool execution anywhere in this codebase yet.

## 1. What's implemented

**Week 1 - planning**
- `POST /api/v1/agent/plan`: an explicit, linear LangGraph workflow
  (`UNDERSTAND_REQUEST -> GENERATE_PLAN -> VALIDATE_PLAN`, no loops, no
  branching, no multi-agent orchestration) turns text into a plan using a
  local LLM (Ollama). The raw LLM output is never trusted - it's always
  parsed and re-validated with Pydantic.
- A fixed catalog of three logical tools (`calendar`, `tasks`, `email`)
  with a fixed set of operations each. Anything outside that catalog is
  rejected with a structured error instead of being silently accepted.
- Requests missing required details (e.g. "schedule a meeting tomorrow"
  with no title) still produce a plan, with the missing fields listed
  instead of an invented value.

**Week 2 - human-in-the-loop approval**
- Every plan generated by `POST /api/v1/agent/plan` is now persisted (in
  memory) and comes back with a lifecycle `status`:
  `awaiting_approval`, `needs_clarification`, or `error`.
- `GET /api/v1/plans/{plan_id}` retrieves a stored plan and its current
  status.
- `POST /api/v1/plans/{plan_id}/approve` / `.../reject` / `.../cancel`
  move a plan through its lifecycle. These are **pure state transitions**
  - no tool is ever called, nothing external happens.
- A minimal React + TypeScript frontend (`../frontend`) to drive the
  whole flow: type a request, see the generated plan, approve or reject
  it.

## 2. Architecture

```
USER
 |
 v
GENERATE PLAN        (LangGraph + Ollama - unchanged from Week 1)
 |
 v
VALIDATE PLAN        (Pydantic - unchanged from Week 1)
 |
 v
STORE PLAN           (app/repositories/plan_repository.py - in memory)
 |
 v
AWAITING APPROVAL
 |
 +-------------------+
 |                   |
APPROVE            REJECT
 |                   |
APPROVED           REJECTED
 |                   |
 +---- NO EXECUTION -+
```

Full request path:

```
Text Input
    |
    v
FastAPI              (app/api/v1/agent.py, app/api/v1/plans.py)
    |
    v
LangGraph            (app/agent/graph.py)
    |  UNDERSTAND_REQUEST -> GENERATE_PLAN -> VALIDATE_PLAN
    v
Ollama               (app/services/ollama_service.py)
    |
    v
Structured Plan      (raw JSON from the LLM)
    |
    v
Pydantic Validation  (app/models/execution_plan.py, action.py)
    |
    v
Plan Repository      (app/repositories/plan_repository.py - in memory)
    |
    v
Approval Service     (app/services/approval_service.py - deterministic
    |                  state machine, no LLM involved)
    v
JSON Response
```

Planning (the AI's job) and approval (a human's job) are deliberately kept
in separate layers: LangGraph only ever produces a plan. Approving,
rejecting, or cancelling that plan is plain application logic in
`approval_service.py` - the LLM is never consulted about, and never
decides, whether a plan is approved.

### Plan lifecycle / state machine

`StoredPlanStatus` (`app/models/stored_plan.py`):

```
                 valid, all info present
                          |
                          v
                 awaiting_approval ------> approved
                          |
                          +--------------> rejected
                          |
                          +--------------> cancelled

  valid, missing info --> needs_clarification   (never approvable)

  failed validation   --> error                 (never approvable)
```

Rules enforced by `ApprovalService` (`app/services/approval_service.py`):

- Only a plan in `awaiting_approval` may be approved, rejected, or
  cancelled. Every other transition (approving a `needs_clarification`,
  an `error`, an already-`approved`, a `rejected`, or a `cancelled` plan)
  is rejected with a structured `409 Conflict` naming the plan's current
  status.
- Approval double-checks that no action still has `missing_information`
  as a defensive backstop, even though `needs_clarification` plans never
  reach `awaiting_approval` in the first place.
- An unknown `plan_id` on any endpoint returns a structured `404`.

### In-memory storage - read this before relying on it

`app/repositories/plan_repository.py` is a plain thread-safe dict behind a
lock. **There is no database.** Every stored plan is lost the moment the
backend process restarts. This is intentional for Week 2 scope - a
durable store is future work, not a bug.

## 4. Prerequisites

- Python 3.11+
- Node.js 18+ (for the frontend)
- [Ollama](https://ollama.com) installed and running locally

## 5. Install Ollama and pull a model

```bash
ollama pull llama3.2:3b
```

Any other Ollama chat model works - point `OLLAMA_MODEL` at it. Larger
instruct models generally produce more reliable JSON.

## 6. Backend: environment configuration

```bash
cd backend
cp .env.example .env
```

Key variables (see `.env.example` for the full list):

| Variable | Default | Meaning |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama server URL |
| `OLLAMA_MODEL` | `llama3.2:3b` | Model tag to use for planning |
| `OLLAMA_TIMEOUT_SECONDS` | `90` | Request timeout when calling Ollama |
| `LOG_LEVEL` | `INFO` | Root log level |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | Browser origins allowed to call this API |

`CORS_ALLOWED_ORIGINS` is a comma-separated list; the defaults match the
Vite dev server. Add your deployed frontend's origin before pointing a
real build at this API - don't widen it to `*`.

## 7. Run the backend

```bash
cd backend
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Open http://localhost:8000/docs for the interactive OpenAPI docs.

## 8. Run the frontend

```bash
cd frontend
cp .env.example .env   # VITE_API_BASE_URL, defaults to http://localhost:8000
npm install
npm run dev
```

Open http://localhost:5173. Type a request, click **Generate Plan**, then
**Approve Plan** or **Reject**.

## 9. API endpoints

### `POST /api/v1/agent/plan`

Request:

```json
{ "text": "Schedule a meeting with my AI team tomorrow at 3 PM and create a task to prepare the demo." }
```

Response (a fully-specified plan - `status` is the plan's *stored*
lifecycle status, not a generic success/failure flag):

```json
{
  "request_id": "b6b6...",
  "plan_id": "8f2c...",
  "status": "awaiting_approval",
  "execution_plan": {
    "plan_id": "8f2c...",
    "intent": "productivity_workflow",
    "summary": "Create a meeting and a preparation task.",
    "status": "ready",
    "actions": [
      {
        "action_id": "action_1",
        "tool": "calendar",
        "operation": "create_event",
        "parameters": {"title": "AI Team Meeting", "datetime": "tomorrow at 3 PM"},
        "missing_information": [],
        "requires_approval": true
      },
      {
        "action_id": "action_2",
        "tool": "tasks",
        "operation": "create_task",
        "parameters": {"title": "Prepare the demo"},
        "missing_information": [],
        "requires_approval": true
      }
    ]
  },
  "errors": null
}
```

- Missing required details (e.g. "Schedule a meeting tomorrow.") ->
  `status: "needs_clarification"`, with the missing field names listed in
  the relevant action's `missing_information` instead of an invented
  value. This plan is stored but can never be approved.
- An unsupported tool/operation, or an LLM response that doesn't parse
  into the schema, -> `status: "error"`, `execution_plan: null`,
  `errors: [...]`, HTTP 200 (the request itself was fine; the *content*
  couldn't become a valid plan). The plan is still stored under
  `plan_id` so it's traceable, but it can never be approved either.
- Ollama being completely unreachable is a real infrastructure failure,
  not a plan outcome -> HTTP 502, nothing is stored.

### `GET /api/v1/plans/{plan_id}`

Returns the stored plan (same shape as `execution_plan` above, wrapped
with `status`, `errors`, `rejection_reason`, `created_at`, `updated_at`).
`404` with a structured `{plan_id, message}` body if unknown.

### `POST /api/v1/plans/{plan_id}/approve`

Approves a plan that is `awaiting_approval`. Returns
`{plan_id, status: "approved", message, plan}`. **No tool is executed.**
`409 Conflict` with `{plan_id, message, current_status}` if the plan is
in any other state (`needs_clarification`, `error`, already `approved`,
`rejected`, or `cancelled`).

### `POST /api/v1/plans/{plan_id}/reject`

Body is optional: `{"reason": "I want to change the meeting time."}`.
Returns `{plan_id, status: "rejected", message, rejection_reason, plan}`.
Same `409`/`404` rules as approve.

### `POST /api/v1/plans/{plan_id}/cancel`

Cancels a plan that is still `awaiting_approval`. Returns
`{plan_id, status: "cancelled", message, plan}`.

## 10. How approval works

`POST /api/v1/agent/plan` never decides approval - it only ever produces
`awaiting_approval`, `needs_clarification`, or `error`. A human (via the
frontend, curl, or `/docs`) then calls `approve`, `reject`, or `cancel`.
That call is handled entirely by `ApprovalService`
(`app/services/approval_service.py`), which:

1. Looks up the plan by `plan_id` (404 if missing).
2. Checks it is currently `awaiting_approval` (409 if not - this is what
   makes an already-decided or not-yet-clarified plan un-re-decidable).
3. Re-checks no action has `missing_information` (defensive; redundant
   with step 2 today, but keeps the invariant explicit).
4. Writes the new status (and `rejection_reason`, if rejecting) back to
   the in-memory repository.

Nothing in this path calls Ollama, LangGraph, or any external tool.
Approving a plan changes its `status` field to `"approved"` - that's the
entire effect.

## 11. Run tests

Tests mock the LLM provider layer (`app.services.ollama_service`) and
reset the in-memory plan repository between tests, so the whole suite
runs without a live Ollama server.

```bash
cd backend
pytest
```

`tests/test_api.py` covers planning (Week 1 behavior, updated for the new
response `status` semantics); `tests/test_plans.py` covers the full
approval lifecycle (store -> approve / reject / cancel, invalid
transitions, 404s, rejection reason persistence).

## 12. Current limitations

- No real execution of any action, ever - approving a plan only changes
  its stored status.
- **Storage is in-memory only.** Restarting the backend loses every
  stored plan. There is no database in this phase.
- No authentication/authorization - anyone who can reach the API can
  approve/reject any plan_id they know.
- Single LLM call per request; malformed JSON is surfaced as a
  structured error, not silently retried forever.
- Time expressions (e.g. "tomorrow at 3 PM") are kept as the LLM's raw
  text, not resolved to a real timestamp.
- Plan quality depends on the chosen local model; smaller models may
  occasionally violate the JSON contract, which surfaces as an `error`
  plan rather than a crash.
- A cold/unloaded Ollama model, or a machine under heavy load, can push a
  single generation past `OLLAMA_TIMEOUT_SECONDS`; raise it in `.env` if
  you see spurious `502`s.
